# Case processing observability

Each instrumented workflow step emits a structured JSON start and completion or failure to Vercel Runtime Logs. Search for the case ID, then filter by `case.version`: this is the Workflow **run ID**, stable for one execution and different after a rerun. It is not the pipeline version or the database cache `revision` (which also changes when a case resolves). Records include the workflow step ID and attempt, so retries of the same step are distinguishable. Runs are also tagged with `case_id` for filtering in the Vercel Workflow dashboard/CLI; if tagging fails the case continues and a warning is logged.

For example, find a case with `vercel logs runtime --environment production --since 30m --query 'AT-185-GA'` in the linked project. For a stalled case, look for a `case.step.started` without a corresponding completion/failure for the same step ID and attempt; a timeout can prevent the final log. In pipelines 3–5, `fetch_proposals` logs each `case.source.started` and `case.source.ready`, `.failed`, or `.error`. The SHA-256 `source.url_hash` identifies a proposed URL without logging it. `case.sources.fetched` and `case.proposals.filed` summarize the batch and rejected proposals. Event batches report their types and last sequence number, not event bodies. Parallel steps can interleave and a retried step can emit the same logical progress again.

During `file_proposals`, `case.proposals.sources_loading` and `case.proposals.sources_loaded` bracket the single verified artifact-tree read, and `case.proposals.matching_completed` reports quote-matching time. These records contain only counts and durations. A start without its completion can identify which part was interrupted; the step's completion also includes rejection audit writes.

In pipelines 3–5 the criticism round starts with a `criticism_index` step of its own: one verified artifact-tree read builds the source index that the four analysts' `source_review` steps then receive, so it neither counts against their time nor repeats at each of their units and retries. `case.criticism_index.built` reports the number of sources, of canonical sources and the characters of the index. Every whole-tree read of a case's artifacts from R2 logs `case.artifacts.read` with the objects listed, files and bytes read, listing time and total duration; a read of 20 s or more is a warning. Several such reads within one step, or one close to the 300 s function limit, show where a step spends its time before it times out.

New cases opting into native research (`COURT_PIPELINE_VERSION=3`) use pipeline 5. Admin reruns and failed-case retries explicitly use the latest pipeline, even when the new-case rollout setting selects an older one; they still require the latest pipeline's preflight configuration. It saves the URLs in the public case timeline before each batch starts and reports each URL’s outcome when the batch completes, making an ongoing batch visible. These URLs are part of the public case record, not operational logs. `case.sources.collection_started`, `case.sources.batch_started` and `case.sources.batch_completed` include counts and event sequence; unreadable links are counted and logged at warning level. A failed fetch step produces no completed-batch event until it succeeds. Retried save steps can repeat log messages, so use the case/run and event sequence to identify the logical update. Existing pipeline 3 and 4 runs retain their original workflow sequence and do not gain the new batch URL updates.

Logs and spans include case ID and run ID. This instrumentation emits only controlled metadata, error type/code and HTTP status when available; it does not emit prompts, source URLs, model outputs, error messages, or source content. Existing framework/provider logs and case audit records have their own data and retention policies. Trace sampling, log retention and platform interruption can leave gaps; the workflow journal and case record remain authoritative.

## Metrics and OTLP

Vercel receives one `case.processing.step.duration_ms` custom-metric point per completed or failed instrumented step attempt, tagged with `step`, `outcome`, `case_id` and `case_version`. Filter it in Observability > Custom Metrics; a count of points measures attempts, not unique steps or completed cases. Vercel's custom metric events can incur Observability charges. Aborted/timed-out steps may not emit a point.

The OpenTelemetry meter emits `case.processing.step.attempts` (counter) and `case.processing.step.duration` (histogram, milliseconds). These use only the bounded `step` and `outcome` attributes to avoid a high-cardinality time series for every case. Correlate individual work through the case/run attributes on logs and spans, or the Vercel metric point. Emission/export is best-effort and must not affect case processing.

Vercel collects the JSON console logs and its native metrics without an OTLP destination. For standard OTLP/HTTP JSON logs and metrics, configure an authorized collector with either `OTEL_EXPORTER_OTLP_ENDPOINT` (the base URL, with `/v1/logs` and `/v1/metrics` appended) or the signal-specific `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` and `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` (full URLs). The base endpoint can also configure trace export. Set standard `OTEL_EXPORTER_OTLP_HEADERS` or signal-specific headers as needed, using secret environment variables; never commit credentials. With no collector endpoint, OTel logs and metrics are not exported. The app attempts to flush completed step telemetry with Vercel `waitUntil`; a killed function can still lose buffered OTLP data. Tracing is registered through `@vercel/otel` and follows Vercel's tracing configuration and sampling.

Consult [Vercel custom metrics](https://vercel.com/docs/observability/custom-metrics) and [drains](https://vercel.com/docs/drains/using-drains) for current limits, retention, access and pricing. Enabling a drain or external collector is an operator decision; this code does not configure one.
